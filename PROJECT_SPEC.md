# Family Finance Ledger — Rebuild Spec

## Why this document exists
This app started as a Claude.ai artifact (a browser demo, not a real hosted app).
It hit real limits: no real database (just a capped, best-effort storage feature),
no real login (sharing means a fully public link), and every code update creates a
new instance that can't see previously entered data. This document is everything
needed to rebuild it properly — a real app with a real database and real login —
without losing any of the logic, data, or design decisions already made.

Two companion data exports sit next to this file:
- `family-finance-data-export.json` — the full current dataset (real bank-derived
  transactions, accounts, goals, liabilities, assets, investments, recurring bills)
- `shopping-tracker-data-export.json` — the companion grocery/shopping item tracker's data

Both were generated by actually running the live seed logic, so they're guaranteed
to match what's in the current app, not a stale intermediate copy.

## Recommended stack
- **Frontend**: React (Next.js recommended for easy Vercel deployment)
- **Database + Auth**: Supabase (Postgres + built-in auth, generous free tier)
- **Hosting**: Vercel (or Supabase's own hosting)
- **Two family members log in separately** (Gowtham, Sanjana) and see/edit the same
  shared household data — this is the #1 reason a real backend matters: proper
  multi-user access control, not a public link anyone can open.

## Core principle: preserve every rule below exactly
The categorization and financial logic in this app was built up over many
iterations, cross-checking real bank statements, payslips, and handwritten notes.
Re-deriving it from scratch would reintroduce mistakes already caught and fixed.
Import the JSON data as-is; re-implement the *behavior* below, not just the schema.

## Data model

### `households`
One row for the family. `base_currency` (default GBP), `exchange_rates` (JSON map
of currency code → rate against base, manually editable, e.g. `{"GBP":1,"INR":0.0095,"USD":0.79,"EUR":0.86}`).

### `users` (via Supabase Auth) → `members`
Each real login maps to a `members` row: `name`, `role` (e.g. "Adult 1", "Spouse"),
`color` (for avatar display). Two members exist today: Gowtham and Sanjana.

### `accounts`
`name`, `type` (Bank Account / Cash / Credit Card / Savings Account / Investment
Account / Digital Wallet), `currency`, `balance`, `owner_id`, `country`, `notes`.
**Important**: several accounts are *derived placeholders* (e.g. a Saver account or
a Monzo account) built from internal-transfer patterns found in statements, not
from a direct statement for that account — their balance is "net of transfers
seen," not a real opening balance. Keep the `notes` field so this stays visible.

### `transactions`
`type` (expense / income / transfer), `date`, `amount`, `currency`, `category_id`,
`subcategory_id`, `description`, `person_id` (who it's for/associated with),
`entered_by_id`, `account_id`, `to_account_id` (transfers only), `recurring`
(boolean), `notes`, `country`, `items` (JSON array, optional — see Receipt Items
below), `created_at`, `updated_at`, `created_by`, `updated_by`.

**Multi-currency rule**: always store the original amount and currency on the
transaction. Never overwrite it with a converted value. Convert to base currency
only at display/aggregation time using the household's `exchange_rates`.

**Transfers are not expenses or income.** A transfer has both `account_id` (from)
and `to_account_id` (to) and must never be counted in income/expense totals.

### `categories` (+ subcategories)
Customizable list, not hardcoded. Current set includes standard categories
(Groceries, Eating Out, Rent/Mortgage, Utilities with subcategories for
Electricity/Gas/Water/Internet/Mobile, Transport with subcategories for
Fuel/Public Transport/Car/Insurance, Healthcare, Education, etc.) **plus**
categories that emerged from real data: `Family Transfers`, `Personal Loans /
Debts`, `Personal Loan Repayment`. See the export for the full current list.

### `recurring_transactions`
Informational list of known recurring bills/income — **does not feed into actual
transaction totals**, only into a separate "recurring monthly commitment" figure.
Fields: `description`, `amount`, `currency`, `category_id`, `subcategory_id`,
`frequency` (weekly/monthly/quarterly/half-yearly/yearly/custom), `account_id`,
`person_id`, `active`, `type` (expense/income), `notes`.
Monthly-normalize by frequency: weekly×52/12, quarterly×4/12, half-yearly×2/12,
yearly×1/12. **Exclude `type: "income"` entries from the "commitment" total** —
that figure means bills going out, not income coming in.

### `assets`
`name`, `type`, `owner_id`, `purchase_date`, `purchase_value`, `current_value`,
`currency`, `country`, `notes`, `valuation_history` (JSON array of {date, value}).

### `investments`
Separate from generic assets — for LIC insurance policies, mutual funds, PPF,
stocks, fixed deposits. Fields: `type` (LIC Insurance / Mutual Fund / PPF /
Stocks / Fixed Deposit / Other), `name`, `provider`, `owner_id`, `currency`,
`invested_amount`, `current_value`, `start_date`, `maturity_date`,
`maturity_amount`, `premium_amount`, `premium_frequency`, `folio_number`, `notes`.
Roll `current_value` into the net worth (assets) total alongside `assets`.

### `liabilities`
`name`, `type` (Mortgage / Car Loan / Personal Loan / Credit Card / Education
Loan / Other), `original_amount`, `current_amount`, `currency`, `interest_rate`,
`monthly_payment`, `start_date`, `expected_end_date`, `account_id`, `person_id`,
`notes`. Include in net worth as a subtraction. Several current entries are
flagged "unconfirmed — not found in either statement" in their notes; preserve
that distinction rather than treating all liabilities as equally verified.

### `goals`
`name`, `description`, `target_amount`, `currency`, `target_date`,
`current_amount`, `monthly_contribution`, `account_id`, `priority`, `owner_id`
(or "shared"), `notes`, `contributions` (JSON array).
Formulas:
- `remaining = max(0, target_amount - current_amount)`
- `months_remaining = max(0, months_between(today, target_date))`
- `required_monthly = months_remaining > 0 ? remaining / months_remaining : remaining`
- `percent = min(100, current_amount / target_amount * 100)`
- Scenario planner: given a hypothetical monthly contribution, `months_to_complete = ceil(remaining / contribution)`

### `budgets`
`category_id`, `person_id` (optional), `amount`, `currency`, `period` (monthly).
Compare against actual same-month spend in that category for a progress bar.

### `shopping_list`
Separate lightweight list: `name`, `checked`, `added_at`. Suggest frequently-
bought items (aggregated from receipt `items`, see below) as quick-add chips.

## Critical business logic to reproduce exactly

### 1. Bank statement import & categorization
Transactions were parsed from real HSBC PDF statements (debit + credit card, two
people) using pattern-matching on merchant description text. If re-importing
future statements, categorize by keyword rules (grocery chains → Groceries, fuel
stations → Transport/Fuel, etc.) — see the `category_id` values already assigned
in the data export as the canonical mapping for merchants seen so far.

### 2. Avoiding double-counted transfers (important — a real bug we hit and fixed)
When both people in a household have accounts and money moves between them, it
can appear as an outflow on one statement and an inflow on the other. **Match by
date + amount** across both people's raw transactions before categorizing; a
matched pair becomes a single `transfer` row (not two expense/income rows).
Unmatched one-sided transfers stay as a regular category (e.g. "Family Transfers")
on whichever side has the record.

Similarly, a person's payment to their *own* credit card (matched by card number
appearing in the current account statement) should become a `transfer` to that
credit card account — not a duplicate expense.

### 3. Salary counted toward the month it's spent, not the month it's paid
Salary is credited at month-end but used to cover the *following* month's
expenses. For any dashboard/budgeting view (not the raw transaction ledger),
bucket `type: income, category: Salary` transactions into `date + 1 month`
(first of next month) rather than their real credit date. **Do not alter the
stored `date`** — only shift which period it's grouped into for display. Handle
month-length edge cases correctly (e.g. Jan 31 + 1 month → Feb, not "Mar 3").

### 4. Receipt item scanning — attach, don't duplicate
When a receipt is scanned/entered with itemized products, it usually corresponds
to a purchase **already present** as a lump-sum transaction from the bank
statement import. Default behavior: search existing un-itemized expense
transactions for a close match (similar date, similar total) and **attach the
items array to that existing transaction** rather than creating a new one. Only
create a new transaction if the user explicitly confirms "not in my statement yet."

### 5. Dashboard filtering
Three independent, combinable filters: **Period** (Month / Year / Financial Year
[Apr–Mar, used for both UK and India tax years] / All Time), **Person**, and
**Category**. Category filter shows total + per-person breakdown + a 6-month
trend chart for that category, replacing the default top-5 category list.

### 6. Net worth
`net_worth = sum(assets.current_value) + sum(investments.current_value) -
sum(liabilities.current_amount)`, each converted to base currency.

## Pages / features to rebuild
- **Dashboard**: net worth hero, period/person/category filters, income/expense/
  cash flow/savings cards, recurring commitment vs one-time spend, top spending
  categories (or category detail view when filtered), goal progress preview,
  quick-action shortcuts (Expense/Income/Transfer/Goal Contribution/Asset/Liability)
- **Transactions**: searchable/filterable list (date range, person, category,
  currency, country), swipe/tap to edit
- **Accounts**: list with balances, transfer between accounts
- **Goals**: list with progress bars, scenario planner (try different monthly
  contributions), edit/delete
- **Investments**: LIC/mutual fund/PPF tracking, invested vs current value, gain/loss
- **More/Settings**: Family members, Categories (+ subcategories, user-defined),
  Recurring transactions, Assets, Liabilities, Budgets, Currencies & exchange
  rates, Scan Receipts (paste-based item entry, attach-to-transaction flow),
  Grocery item insights, Shopping list, Data export (CSV/JSON), theme
- **Companion app — Shopping/Grocery tracker**: intentionally separate from the
  finance app's account balances (no double-counting risk). Tracks item-level
  purchases (trip = store + date + items[]) independent of bank transactions.
  Dashboard shows spend by category/store/item over time.

## Design language
Mobile-first, bottom navigation (Dashboard/Transactions/Accounts/Goals/More),
floating "+" action button. Palette: deep teal (`teal-900`/`teal-800`) primary,
amber (`amber-500`) accent, rose for expenses, emerald for income. Display font:
Fraunces (serif) for headlines/large numbers; IBM Plex Mono for monetary figures;
Inter for UI text. Cards are white, rounded-2xl, subtle borders — avoid a
spreadsheet-like dense-table feel.

## Multi-currency
Support GBP, INR, USD, EUR minimum, extensible. Base currency GBP today, user-
changeable. No live FX API is currently wired up — exchange rates are manually
entered/edited in Settings. If adding a live rate feed later, keep manual
override per-transaction so historical transactions are never silently
recalculated when rates change.

## Data migration
Import `family-finance-data-export.json` and `shopping-tracker-data-export.json`
directly as the initial seed — the shapes above map close to 1:1 with the JSON
fields (snake_case here, camelCase in the export; a straightforward key rename).
